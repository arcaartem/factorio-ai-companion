Version: 0.20.3
Date: 2026-07-28
  Bugfixes:
    - companion_position (and the position field companion_list embeds) reported
      math.floor(pos.x * 10) / 10 - truncated to one decimal place, not rounded - which live-probed
      a 0.103-tile error against the companion's true position (matched by unit_number, so it
      wasn't a stale-entity artifact). Both handlers now report the entity's exact pos.x/pos.y.
      The same truncation was also flooring reported positions in world_scan, world_enemies and
      resource_list; all three now report exact coordinates too. Health percentages, on-screen
      distances and progress percentages floor by design and are untouched.
    - building_empty / building_fill could resolve a spilled item-on-ground entity as the
      "container" - resolve_target picks the nearest surviving match by name/force alone, with no
      requirement that it actually have an inventory the transfer loop can use. Live evidence:
      building_empty returned {"extracted":0,"entity":"item-on-ground"} while a chest one tile away
      still held 50 untouched plates. Both call sites now pass a predicate requiring at least one
      of the inventory indices the loop actually reads/writes (empty: chest, furnace_result,
      assembling_machine_output; fill: chest, furnace_source, assembling_machine_input), so an
      item-on-ground entity - which has none of them - is never picked. Each not_found message now
      names the real problem ("No container with an output/input inventory found") instead of a
      generic "Not found"/"Could not insert".
    - building_empty stopped reporting `full` when the COMPANION, not the container, was the
      limiting factor. T-019 (0.13.5) added that flag; the 0.19.0 single-target refactor dropped
      it along with the fan-out sweep it was set inside, so a caller saw {"extracted":5} against a
      request of 50 with nothing to distinguish "your inventory is full" from "the chest only had
      5". Restored: `want` is already capped at what the container holds, so a short accept means
      the companion refused the remainder. building_remove's equivalent flag was never affected.

Version: 0.20.0
Date: 2026-07-28
  Changes:
    - Removed the wololo command (fac_action_wololo / action_wololo). There is no player action
      that converts an enemy at any distance, so it could not be brought to player parity by
      bounding its radius the way other companion abilities were. It also converted a

      now unused by data.lua

Version: 0.19.0
Date: 2026-07-28
  Bugfixes:
    - building_empty extracting items always errored with "count must be positive" even though
      the extraction itself had already succeeded. defines.inventory.{chest, furnace_result,
      assembling_machine_output} are {1, 3, 3} - index 3 aliased twice - so once the request was
      satisfied at index 3 the inner loop visited it again with want=0 and insert{count=0} raised
      after the items had already moved. The inventory index list is now de-duplicated and the
      inner loop breaks before a zero-count insert; count<=0 is now also rejected up front as a
      clean error instead of falling through `tonumber(args[3]) or 10` (0 is truthy in Lua)
    - building_rotate reported {rotated = true} even when the entity never turned. It now reads
      the direction back off the entity after assigning and reports failure ({error = "Rotate had
      no effect"}) when the read-back doesn't match what was requested; an out-of-range direction
      index (anything but 0-3) is now rejected instead of silently becoming north
      (u.dir_map[7] == nil)
    - building_remove resolved its target by requested coordinates, not the entity's actual
      position - since create_entity can snap elsewhere, a place/inspect/remove loop could strand
      buildings and drain the companion's inventory retrying at a dead coordinate. Every building
      command below now goes through the new u.resolve_target helper, which picks the nearest
      surviving match by distance (find_entities_filtered's order is engine chunk order, not
      distance order - the old `es[1]` pick was arbitrary) and, for every command that ACTS on the
      entity, checks reach against the resolved entity's position rather than the requested point.
      building_info is the one deliberate exception: it passes reach = false, because a read-only
      inspection is not an action - the carve-out is an explicit argument at the call site rather
      than an omission
    - fuel/fill/empty checked reach against the requested x/y instead of the entity they ended up
      acting on, so a companion could be told "too far" for an entity that was actually in range,
      or vice versa. Fixed via the same resolve_target path
    - building_fill had the same zero-count defect as building_empty: 0 survives
      `tonumber(args[3]) or 10` (truthy in Lua) and reaches insert{count = math.min(0, have)},
      which raises "count must be positive". It now rejects count<=0 up front like empty does
    - building_fuel's filter listed `"burner-inserter"` as a prototype TYPE, but a burner
      inserter's actual type is `"inserter"` - the entry never matched anything, so burner
      inserters were unfuellable. Fixed by filtering on `"inserter"` (the fuel-inventory predicate
      still excludes electric inserters)
  Changes:
    - fill and empty now resolve and act on a single nearest entity instead of fanning out across
      every match in radius until the count is satisfied - the old fan-out could split one
      `inserted`/`extracted` count across several entities, and empty's unrestricted radius-5
      search could drain the connected player's own inventory (defines.inventory.chest ==
      character_main == 1, so a character is a valid "chest"). Both now take an optional trailing
      entityName argument to narrow the match, and exclude character entities by default
    - building_fill previously had no force filter at all and is now restricted to the companion's
      own force. That closes filling an enemy's containers, but also narrows it: neutral
      containers (crash-site wreckage) can no longer be filled, though empty still reads them.
      Deliberate asymmetry - loot unowned wreckage, but only stock your own buildings
    - building_place, building_fuel, building_fill, building_empty, building_rotate and
      building_recipe success payloads now include the resolved entity's actual `position` (and
      `entity` name where it wasn't already reported), so a caller can act on where something
      really is rather than where it was requested
    - building_can_place's RCON template gained the `direction` argument its Lua handler already
      accepted, so it now answers for the direction actually being placed instead of always north
    - building_place_status can now report a finished placement. The build queue entry is pruned
      on the same tick the entity is created, so a poll arriving afterwards had no way to read the
      outcome at all; the result is now recorded in storage.build_results before the entry is
      deleted (same idiom as harvest/combat) and reports placed, entity, the entity's real
      position, the originally requested position, and a reason of placed/blocked/stopped

Version: 0.18.0
Date: 2026-07-27
  Features:
    - The companion can harvest WOOD. resource_mine and resource_mine_until now accept the token
      "wood" (or "tree") and chop trees, where before they replied {error = "No resource"}: both
      fac_resource_mine and queues.start_harvest seeded their pool with
      find_entities_filtered{type = "resource"}, and a tree is type = "tree". This was a
      capability gap, not a queue bug - no change to the harvest tick was needed, and a tree
      actually suits it better than ore does, since a tree is genuinely consumed when mined
      (entity.valid -> false, which is exactly the advance condition) whereas an ore tile only
      decrements amount and stays valid
    - resource_nearest accepts "wood"/"tree" too, so a caller can locate a tree and then mine it
      through the same pair of calls it already uses for ore
  Changes:
    - Wood is the one harvestable that cannot be selected by name - trees ship dozens of
      prototypes (tree-01 .. dead-dry-hairy-tree), so {name = "wood"} matches nothing. The
      ore-by-name vs tree-by-type split now lives in one helper, u.resource_filter, which
      resource_nearest, world_nearest and start_harvest all route through. resource.lua and
      world.lua had each carried a private copy of the resource alias table and only world.lua
      knew about trees; those copies are gone
  Bugfixes:
    - resource_nearest no longer risks raising on a tree. `amount` is a resource-only LuaEntity
      property, so it is now reported only for entities of type "resource" and omitted for trees

Version: 0.17.0
Date: 2026-07-26
  Bugfixes:
    - resource_nearest and world_nearest now actually return the NEAREST match. Both scanned a
      +/-200 square with limit=100 and then picked the minimum from whatever came back, but
      find_entities_filtered's limit truncates in the engine's chunk order with no distance
      ordering - so the true nearest could be excluded from the sample outright. Probed live
      returning iron-ore at distance 155 while iron-ore sat at 85.5. Both now grow an unlimited
      circular search (8 -> 16 -> 32 -> 64 -> 128 -> 200), which is complete by construction:
      whatever the first non-empty circle contains, everything omitted is farther than its
      radius. The near case stays cheap; only genuinely empty surroundings pay for a wide scan
    - resource_nearest no longer floors the coordinates it returns. Ore sits at tile centres
      (x.5, y.5), so flooring reported a point ~0.71 tiles off the actual entity - spent
      straight out of the engine's 2.7-tile resource_reach_distance before the caller had
      walked anywhere. Reported distance is likewise no longer floored, which had it
      under-report and skip a needed walk
  Changes:
    - world_nearest's water branch searches the same expanding circle as the entity branches
      instead of a limited square, and reports an unfloored distance

Version: 0.16.0
Date: 2026-07-26
  Bugfixes:
    - Fixed the harvest queue pinning the companion in place forever: the engine reverts
      walking_state every tick while mining_state.mining is true, so a walk/combat queue
      trying to move the companion could never actually move it. The harvest tick now yields
      to an actively-moving walk/combat queue instead of fighting it, and re-asserts mining
      once movement stops
    - Fixed harvested count staying at 0 forever: mining_state.mining stays true for as long
      as the ore tile has ore left (it's a per-amount decrement, not a per-ore event), so the
      old "mining stopped -> count" guard never ran. Inventory deltas are now counted every
      tick instead
    - Added a 15s stall-guard timeout to the harvest queue so it can never hang indefinitely
      even if the above two paths are both blocked
    - start_mining_next now skips pool entities beyond resource_reach_distance - the pool is
      seeded from a wider radius-3 search than the engine's actual mining reach (2.7)
    - companion_stop_all now also clears mining_state, not just the queue and walking_state
    - resource_mine_status now reports a finished queue's harvested/target/reason instead of a
      bare {active=false}. The queue is deleted on the same tick its final ore is counted, so
      the terminal poll previously had no way to read the outcome at all - which made
      mine-until's success path return 0 even once counting itself was fixed
    - fac_resource_mine now propagates start_harvest's error instead of always reporting
      mining:true/status:"started"
  Changes:
    - mine-until's walkTo now also treats the walk queue reporting active:false as arrival,
      not just a hard-coded distance check - a companion could land between the two
      thresholds and spin for the full walk timeout with no queue behind it
    - mine-until's mining timeout path now uses the harvested count from the stop response
      instead of the last (potentially stale) status poll
